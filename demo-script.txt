QUE VA A PASAR EN ESTA DEMO (léelo antes de empezar):
Vamos a demostrar, en el cluster real (no grabado, no simulado),
que Harbor bloquea activamente imágenes inseguras y acepta las que
cumplen la política. Se muestran dos casos de éxito y dos de falla:

  1) Una imagen con vulnerabilidades se sube sin problema (éxito),
     pero se bloquea al intentar descargarla en un entorno estricto
     (falla intencional = la política funcionando).
  2) La misma imagen SI se puede descargar desde un entorno menos
     estricto (éxito), probando que la separación de entornos es real.
  3) Una imagen sin firma digital es rechazada en producción (falla
     intencional), mientras una firmada se descarga sin problema
     (éxito).
  4) Un pod real de Kubernetes descarga una imagen usando una
     credencial de robot de solo lectura (éxito end-to-end).

POSIBLES FALLOS QUE PUEDEN APARECER (no son errores tuyos, son del
comportamiento real del cluster bajo carga):
  - Comandos lentos o "no route to host" justo después de encender
    las VMs: el cluster necesita unos minutos para estabilizarse.
  - Un nodo worker puede aparecer NotReady si la VM se congeló.
  - Harbor puede responder 502 si harbor-core se está reconectando
    a la base de datos tras un reinicio reciente.
  - El escaneo de una imagen nueva (no usada antes) puede tardar
    1-3 minutos; por eso la demo usa solo imágenes YA escaneadas.
  - El webhook depende de un sitio externo (webhook.site); si no hay
    internet en el salón, ese bloque se omite y se explica por qué.

REGLA DE ORO: si algo falla, no lo ocultes. Dilo en voz alta y
explica qué está pasando; es evidencia de que entiendes el sistema.

================================================================
 PLAN B — QUE HACER SI ALGO FALLA EN VIVO
================================================================

PROBLEMA: comando lento o "no route to host"
CAUSA: el cluster no tuvo tiempo de estabilizarse
QUE HACER: decir "el cluster acaba de recibir carga, démosle un
  segundo" y ejecutar "kubectl get nodes" mientras esperas 10-15 seg

PROBLEMA: un worker aparece NotReady
CAUSA: la VM se congelo
QUE HACER: tener una segunda ventana lista con acceso al
  hipervisor para reiniciar esa VM sin salir del tema; mientras,
  seguir con otro bloque que no dependa de ese nodo

PROBLEMA: harbor.lab.local no responde (502 o timeout)
CAUSA: harbor-core reconectando tras carga reciente
QUE HACER: tener una pestana de navegador ya abierta apuntando a
  Harbor para no perder tiempo escribiendo la URL; si persiste,
  mostrar el archivo /tmp/prueba-bloqueo-vulnerabilidad.txt como
  evidencia de que ya funciono antes

PROBLEMA: el escaneo de una imagen tarda mucho
CAUSA: Trivy necesita tiempo real de escaneo
QUE HACER: no subir una imagen nueva sin escanear durante el
  examen; usar solo las ya escaneadas (nginx:1.16, alpine:3.20,
  hello-world)

PROBLEMA: el webhook no muestra nada en webhook.site
CAUSA: la pestana expiro o se perdio la URL
QUE HACER: tener guardada la URL en un archivo aparte, y una
  captura de una notificacion previa como respaldo.
Abre una pestaña nueva en tu navegador y entra a https://webhook.site
Haz clic en New Webhook.
Llena el formulario:
Name: notificacion-eventos
Notify Type: HTTP
Endpoint URL: pega la URL que copiaste de webhook.site
Event Type: marca al menos Pushing artifact y Scanning completed
